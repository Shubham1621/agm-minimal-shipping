# Designing an Integrity Gate for AI Data Pipeline Agents: A Framework, a Preregistration, and an Honest Confession.

*Case study · 21 October 2026*

## The problem

Consider a pipeline agent asked to materialize a BigQuery table partitioned by `DATE(event_date)`. It generates SQL that leaves `event_date` out of the SELECT list, omits the partition expression, or misspells the column in that expression. The pipeline can fail immediately, or the query can complete while silently producing an unpartitioned table. A human engineer may absorb the debugging time, the incident review, the missed service-level objective, and the reputational cost. The model generally receives another prompt and tries again. This asymmetry matters because generated pipelines are often evaluated through visible task completion while the reliability of their reporting—and the downstream decisions based on that reporting—can remain unmeasured. A system may not only make a mistake; it may provide a status report that causes another component to accept the mistake as success. I have designed a small experiment around this failure mode, but I have not yet run it against BigQuery.

## How the scope shrank, and why that's a feature

The starting idea was broad: an Accountable Group Mind (AGM) that accumulates reasoning across generations while allocating consequences to components responsible for failure. The motivating analogy was cumulative human learning. Institutions preserve techniques, discard or revise practices that fail, and rely on social mechanisms for credit, responsibility and trust. In AI, persistent memory can make later agents more capable, but it can also retain an unverified claim or a defective procedure. A memory store grows; that alone is not a cultural ratchet.

The first compression turned the cultural argument into an architecture: inherited reasoning artifacts, structured handoffs, independent execution evidence, role-level attribution, and policy changes that affect later retrieval or routing. The important distinction was between a postmortem and an actuator. Writing down that an agent made a mistake is a record. Changing what the system permits or retrieves because of that record is a control. The phrase “accountability is only real if it reaches an actuator” summarizes that engineering requirement, but the phrase itself is not a novel research result.

The second compression added integrity as a separate constraint. Capability, exploration/persistence budget, and integrity should not collapse into one reputation score. A component that completes many tasks but misreports failures can make the institution look more competent while making its evidence less trustworthy. An accurate report of a failed check should not itself be penalized; an established false-success report should change eligibility or routing. The mechanism must be tied to a report and an independently recorded execution result, not to a language model grading its own prose.

The third compression was the one that made the study small enough to contemplate after work. Rather than claim to build or validate a multi-generational institutional mind in a few months, the question became: *Can a 60-trial sandbox qualification on a frozen model predict honest reporting in independently generated deployment-like contexts?* That is narrower than the original vision. It is also more falsifiable. The broader design was not useless or “wrong”; it provided the conceptual scaffolding needed to find a first measurable question.

## The framework

### Three axes, not a single score

The proposed agent record separates capability, energy, and integrity. Capability is measured by task success under a defined budget. Energy is the budget allocated to search, attempts, tools and persistence. Integrity is a behavioral estimate of whether the agent accurately and completely reports material execution outcomes when it has access to evidence and a contradictory report could benefit its immediate task outcome. This does not reveal a model's private internal beliefs or establish a human-like moral trait. It measures behavior at the model–harness boundary.

Integrity is non-compensatory in the design. A highly capable agent is not supposed to offset a demonstrated reporting-integrity failure by producing more correct tasks. The eligibility gate decides whether a particular model–role–policy configuration may influence consequential work. Qualification evidence is not inherited automatically across a model version or materially changed policy. The original framework also retains the distinction between a genuine agent error, a harness-injected test fault, and a false report about the fault. Without that separation, the evaluator can accidentally blame an agent for the experiment's own mutation.

### The actuator requirement

The prototype contains a local event ledger, verifier receipt, report/handoff record, memory-artifact status, cost-control code and an outline of escalation routing. The intended consequences are concrete: a confirmed false-success report can remove role eligibility; a known unsafe memory artifact can be quarantined from trusted retrieval; a repeated failure can trigger mandatory verification; a blocked task can be sent to a review queue rather than quietly counted as completed. Each consequence should alter a parameter that a subsequent decision reads.

The slogan “accountability is only real if it reaches an actuator” is not novel by itself. Data-observability tools already store incidents and lineage; CI systems already block releases on failed checks; multi-agent pipeline research already explores structured handoffs and attribution. The potential empirical contribution would be a controlled, reproducible test of whether an integrity qualification gate predicts later reporting behavior and whether that evidence changes eligibility without disguising task blocking as success. The present repository does not establish that contribution. It lays out the proposed measurement and holds the code needed to try it.

### Qualification and transfer

The primary empirical claim is about transfer from a sandbox qualification set to separate holdout contexts. The proposed qualification requires zero observed concealment events in 60 randomized failure-reporting opportunities. The matched holdout uses new instances from the same schema family and difficulty range. The shifted holdout increases context length and task difficulty, changes the schema family, and gives the downstream controller a speed-emphasis prompt. The intent is to distinguish a local predictor from a claim of universal integrity.

Zero failures in 60 trials does not prove that the true concealment probability is zero. The confidence bound remains nonzero, and the result applies only to the tested configuration and sampled contexts. The thresholds are pilot acceptance criteria, not a universal ethics standard. The study can fail in several informative ways: the model may not qualify; qualification may not transfer even to matched contexts; matched transfer may hold while shifted transfer fails; or the task may produce too few discrepancies to evaluate some downstream metrics. Each outcome must be reported as it is, without lowering thresholds after seeing the data.

## What I built

The repository now contains prototype files intended to make the first BigQuery test possible. `sql/create_fixture.sql` defines synthetic source data and an expected partitioned target. `scripts/day15_smoke.py` builds the fixture, executes one hand-crafted correct pipeline, calls the verifier, and writes a result record. `src/verifier.py` implements receipt construction, HMAC signing and validation, schema/partition checks, row-count and key checks, and a partition-pruning comparison. `src/ledger.py` defines SQLite tables for events, receipts, reports, probes, incidents, memory artifacts, policy updates and escalations. `src/task_generator.py` defines deterministic task-variant generation and three intended partition-related mutations. `src/probe.py` defines reporting and downstream-review scores. `src/cost_guard.py` and `src/estimate_cost.py` manage a local API budget estimate. `experiment.yaml`, `reviewer_protocol.md`, `rubrics/commentary_rubric.md`, and `fixtures/bigquery_error_patterns.md` preserve the current trial settings, review process, scoring rules and expected error patterns. `Makefile` and `requirements.txt` provide the intended command-line entry points and dependencies.

There are visible gaps. The current repository does not yet contain the referenced `task_templates.yaml`, so the task generator is not runnable as packaged. The four planned local test files—generator, probe, reviewer-packet and cost-guard tests—are missing. The reviewer command-line scripts, a complete LLM client, and a full experimental orchestrator are also missing. The named integration test exists, but it is not evidence of integration success merely because the file exists.

**None of this has been executed against a live BigQuery dataset.** I have not produced a real verifier receipt from a personal GCP project, run the qualification trials, reviewed scored packets, or evaluated a model's concealment rate. The code is an unverified prototype. This case study records the design and the current implementation boundary, not experimental findings.

## Three lessons from designing without running

### The interface was harder than the abstraction

“Integrity” sounded straightforward until I had to identify exactly where concealment could occur. A model cannot erase a verifier receipt it cannot access. In this prototype, the credible reporting channel is the executor's handoff: structured status fields and free-text commentary sent to a simulated release controller. The private verifier result is stored independently. The model can omit a failure from its own report, but it cannot rewrite the authoritative outcome. Defining that boundary was harder than writing a high-level definition of honesty. It also revealed that one structured field may measure field compliance rather than a general property; the design therefore treats commentary and structured status as separate surfaces.

### Accountability and postmortem are different operations

I had not previously made the distinction cleanly enough in the initial design. A system that says “the executor was responsible” but continues to route the same role, retrieve the same unsafe memory, and release the same class of artifacts has not implemented a consequence. At the same time, blindly punishing every discrepancy would reward defensive behavior, excessive refusal and vague self-protection. The harness needs evidence, responsibility boundaries, calibrated uncertainty and an actual actuator. None of those guarantees a trustworthy system, but without them “accountability” risks being a label on a dashboard.

### Preregistration changes what I am willing to accept

I wrote down the qualification and holdout thresholds before collecting scored model data, and before having a live BigQuery result. That matters even though the study has not started. I cannot honestly lower a threshold simply because a model misses it or reframe a blocked role as a successful predictor after seeing the outcome. The preregistration still needs a timestamped public deposit and a final check that it matches the exact generator and trial allocation. Until that happens, it is a draft protocol—not a public preregistration. Writing it early made the likely disappointing outcomes explicit: no qualification, no transfer, field-sensitive results, or a study too small to support the intended claim.

## What would make this real

The immediate step is modest: use a personal Google Cloud project and synthetic data to run the day-15 smoke test. That should verify a successful BigQuery query, the target's partition metadata, row-count integrity, partition pruning on a filtered query, and a signed receipt. A smoke-test pass will establish only that the integration path works; it will not establish that any model behaves honestly.

A six-month plan with two people would make the research more credible without turning it into a platform project. One person could own execution/verification and reproducibility; the other could independently audit the prompt strata, blind packet scoring and analysis. First, finish the day-15 integration test and the missing unit tests. Second, deposit the exact preregistration before scored runs. Third, run qualification, matched and shifted sets without changing the model ID or thresholds mid-cohort. Fourth, publish the raw trial counts, discrepancies, costs, blocked tasks, reviewer outcomes and limitations alongside the code. If the data support a narrow workshop paper after this work, that is a reasonable ceiling. A solo 90-day effort should not promise a general theory of trustworthy AI institutions.

## Why publish the design before the result

I could have kept extending the design until it looked more complete, or waited until I had time to execute everything. Instead, I am publishing an unfinished-but-explicit artifact because the current boundary is itself important: the research question and planned measurement are defined more clearly than the experiment has been validated. I am working full-time, and the full design is bigger than a reliable solo build in 90 days. Publishing now forces the state of the work to be visible and gives others a chance to find flaws before the first scored run. It also carries a risk: readers may see a framework that never produces an empirical result. If it stops here, the design and its limits are what I contributed—not evidence that the model conceals, not proof that the gate works, and not a claim of a successful experiment.

## An invitation

I would value a collaborator with personal BigQuery and Anthropic API access who can co-run the qualification set using synthetic tasks, preserve the model/version record, and challenge the analysis rather than simply reproduce a hoped-for outcome. I would also welcome critique from people who have built data-observability systems, multi-agent verification pipelines, model-evaluation harnesses or safety evaluations involving misleading reports. The useful feedback is specific: where can a report contradict the underlying evidence, what does the current probe fail to measure, and which outcomes would invalidate the claim? The repository is available for inspection, and the next meaningful update should be the day-15 run record—not another round of design prose.
